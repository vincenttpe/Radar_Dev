# Demo 規劃（2026-10-16）

**原則：Demo 以計畫書為主軸**（「結合 LLM 情境理解之高隱私智慧照護 AI 助理系統」，115 年度智慧雨林產業創生補助計畫，限閱文件，不放進 repo）。計畫書寫到的功能照計畫書的順序展示；本 repo 其餘的功能（知識圖譜體適能等級、Profile 權限、改寫層等）**視情況揭露**：被問到、或剛好能回答審查意見時才拿出來，不排進主流程。

KPI 與查核點已整理在 `08_KPI與查核點.md`，這裡不重複，只標出 Demo 要對到哪一項。

## 11 月中甲方 Demo（2026-10-19 決定）

**主軸是雷達偵測結果的文字報告**：事件摘要、處置提示、照護紀錄草稿、使用趨勢，全部以**官網 Dashboard** 呈現。畫面由 Dashboard 負責人（James）做，本 repo 提供資料與文字；對接方式見 `16_Dashboard對接說明.md`。

| 項目 | 決定 | 為什麼 |
|---|---|---|
| 知識圖譜 | 只揭露為「開發中」，讓甲方知道之後有新功能。現場用 `demo/kg_demo.html` 示範**一次**人工輸入量測值的例子，標明是人工輸入、換算規則是草案、知識圖譜尚未核准；不放進 Dashboard，也不顯示正式等級 | 知識圖譜還沒核准（K-2），雷達也還量不到這些指標（`09_換算規則草稿.md`）；一顯示等級就會被問數字從哪來 |
| 在地模型 | 用**事件提問**讓甲方感受到 Jetson 上的在地模型：照護人員打字問（例如「早上有人跌倒嗎」），模型只選固定題目，先問「您是想問……嗎？」，確認後才顯示答案；答案由事件事實套固定句型，畫面標出模型名稱與耗時。對應不到就列出選單讓人點 | 初期的報告用範本就夠，但後期推廣智慧照顧醫療平台，需要讓人感受到本地模型；選題號不寫答案，模型出錯也不會寫錯事實。也是計畫書應用情境 1（自然語言查詢） |
| 照護紀錄改寫 | 不排進這次 Demo（`care_record.py` 保留） | 2026-10-19 只選事件提問一項 |
| 對接 | `radar-caregiver --json`（報告）、`radar-caregiver --trend --json`（趨勢）、`radar-ask --json`（提問） | 先有一份能跑的輸出，和 James 討論才有東西可以對 |
| 測試資料 | 模擬資料留在 repo（CI 與 Demo 用）；10/19 實機操演與 5 天實測資料只在本機跑，先用 `radar-field-data mask` 遮罩，不 commit；跑出的結果整理成「測試結果摘要」給團隊看，不含 MAC 與原始資料 | `REVIEW.md` 3.3：真實資料不進 repo |

**事件提問（`radar-ask`，`src/radar_agent/event_ask.py`）**：六題，答案句型是 2026-10-19 的草稿，**待確認**（單向門「給讀者的輸出與用語」）。

| 題目 | 答案寫什麼 |
|---|---|
| 有沒有人跌倒？ | 跌倒警報次數與時間、語音回覆沒事次數；有主動呼救時另寫一句「另有主動呼救 N 次」，不算進跌倒 |
| 有沒有人主動呼救？ | 主動呼救次數與時間 |
| 有沒有人待太久？ | 久待警報次數與時間 |
| 用了幾次？最久待多久？ | 使用次數、最長一次；使用途中斷線、資料結束時仍有人在內 |
| 裝置有沒有斷線？ | 斷線時段、裝置錯誤 |
| 有哪些警報？要怎麼處理？ | 和【處置提示】同一份，前面補上事件種類 |

- 沒有資料時，每一題都回「沒有收到資料，無法判斷」，不回「沒有」。
- 每一題都寫出斷線時段（含資料結束前斷線：最後一筆是 offline 就算，`Summary.ended_offline`）與無法判讀的紀錄；有斷線時次數一律寫「在線期間……」。句子和【事件摘要】共用 `caregiver.py` 的同一份寫法（2026-10-19 審查後修正）。
- 題目不解析「今天早上」這類時段：答案開頭有日期，JSON 另附 `from`、`to`，由 Dashboard 標出答案涵蓋的時間。
- 答案也要通過輸出檢查（`check_output`）；沒過就不顯示。
- 不保存讀者打的原文（可能有姓名），只記對到哪一題。
- 準確率用 `radar-model-eval --event-questions` 量（15 題，含「他今天血壓多少」這類應該對不到的題目）。

還沒決定：模型實測的時程（筆電先量或等 Jetson）、答案句型（草稿）、Dashboard 用哪種介面接（週一清單 4-1、4-2）。

**2026-10-19 審查後的決定**：斷線與無法判讀的提醒每題都要有，輸出檢查加嚴（斷線時久待也不能寫「0 次」、不能寫「裝置都在線」）；問跌倒時另提主動呼救；不解析時段；「在 Jetson 本機執行」照部署設定顯示；`local_model.py` 列入單向門「個人資料的流向」。

## 計畫書的主軸（Demo 要講的故事）

1. **場景**：浴廁等單人使用的高隱私空間，不用攝影機（計畫書「應用主題」A2、「機構場域驗證作法」）。
2. **三項互補的安全監測機制**：雷達偵測疑似跌倒、長者主動語音呼救、異常滯留警示（審查意見回覆第 3 項）。
3. **從警報到溝通**：偵測到疑似跌倒先用語音問「您還好嗎」，回答沒事就不必到場（「下一個挑戰：如何超越警報」）。計畫要減少的是不必要的確認、重複通知與紀錄作業，不是減少真正緊急事件的到場處置。
4. **把感測轉成照護語言**：決策建議定位為照護人員的輔助資訊，輸出**事件摘要、處置提示、照護紀錄草稿**（場域驗證指標「決策建議輸出」、審查意見回覆第 20 項）。
5. **應用情境 2：從日常活動發現異常**：比對上週與本週的活動模式，提早預警。
6. **應用情境 1：自然語言健康報告與查詢**：照護者直接用自然語言問系統。

### G1 用語（2026-10-16 確認並實作）

計畫書的例句是「偵測到接近地面姿態持續 30 秒，未取得有效語音回應，請到場確認」。目前的裝置事件**沒有姿態持續時間**，只有「雷達偵測、等候 10 秒無回應」（`delaysec` 10），所以草稿照裝置事件實際有的事實寫，不寫 30 秒：

| 事件（裝置事件） | 處置提示 | 照護紀錄草稿 |
|---|---|---|
| 跌倒警報：雷達偵測、無回應（fall／radar／timeout） | 請立即到場確認。 | 09:02 1 號廁所雷達偵測到疑似跌倒，語音詢問 10 秒未獲回應。 |
| 跌倒警報：雷達偵測、回覆求救（fall／fusion） | 長者回覆需要協助，請立即到場。 | 09:02 1 號廁所雷達偵測到疑似跌倒，長者語音回覆需要協助。 |
| 主動呼救：語音確認或無回應（fall／speech） | 長者主動呼救，請立即到場。 | 09:02 1 號廁所偵測到主動呼救。 |
| 回覆沒事（resolved／noNeedHelp） | 長者回覆沒事，警報已解除；可視情況前往關心。 | 09:03 長者語音回覆沒事，警報解除。 |
| 起身解除（resolved／standUp） | 已偵測到起身，警報已解除。 | 09:03 偵測到長者起身，警報解除。 |
| 久待警報（longstay） | 停留超過設定時間，請前往查看。 | 09:20 1 號廁所停留超過設定時間（久待警報）。 |
| 裝置斷線 | 這段時間無法判斷是否有跌倒，請通知資訊人員。 | 09:10–09:40 裝置斷線，期間狀況不明。 |

實作補充：沒有送 `delaysec` 時，紀錄寫「語音詢問未獲回應」，不補 10 秒；規格外的跌倒來源組合一律寫「請立即到場確認」與「HH:MM 地點跌倒警報」，不猜是哪一種；`resolved` 的 trigger 不是 noNeedHelp 或 standUp 時沒有對應句子，只計入摘要。

### G3 規則（2026-10-16 實作並確認）

`radar-caregiver 紀錄檔 --place 地點 --trend`：以資料的最後一天為準，最後 7 天與再前 7 天比較。

| 規則 | 暫定值 | 為什麼 |
|---|---|---|
| 哪些日子列入比較 | 當天裝置在線至少 23 小時 | 沒有資料不等於沒有使用；在線不足的日子寫「在線不足，不列入」，不當成 0 次 |
| 每週至少幾天 | 5 天 | 不足就寫「可比較的天數不足，無法比較」，不硬算 |
| 比較什麼 | 每日使用次數、凌晨（00:00–06:00）使用次數的平均 | 計畫書情境 2 的示意是夜間活動變化；停留時間先不比 |
| 什麼時候寫「增加／減少」 | 平均每日差距至少 1 次，**而且**至少是前一週的一定比例：每日總次數 **30%**（2026-10-16 決定）、凌晨使用次數 50%（前一週為 0 時只看差距） | 小變化寫「差不多」，避免一點波動就提醒 |
| 結尾 | 「這是場域的統計，沒有個人 ID，不代表特定長者；供照護人員參考。」 | 多人使用的地點不推測是誰（`02_目標架構.md`「輸出的對象」） |

兩週模擬資料的結果：每日使用次數 7.8 對 6.9 次，差距不到 1 次，寫「差不多」；凌晨使用 2.0 對 0.9 次，寫「增加」；10/10 斷線 2.5 小時，不列入。

決定紀錄：

1. ~~門檻~~：2026-10-16 決定每日總次數改用 30%，凌晨維持 50%。注意每天 7 次變 9 次（多 29%）仍差一點不到 30%，照樣寫「差不多」；6 次變 8 次（多 33%）寫「增加」。
2. ~~用語~~：2026-10-16 決定**不加提醒**，「增加／減少」之後不接任何句子，只陳述。
3. ~~已知限制~~：跨過午夜的使用會被切成兩天，可能各算一次，2026-10-16 決定**可接受**。時間戳沒有時區（A4），照原樣以 00:00 分日。

`demo/kg_demo.html`（`python demo/kg_build.py` 產生）：**全部是模擬資料**，用來在內部確認知識圖譜這段 Demo 要有哪些功能。現有的 10/19 實測資料只有浴廁裝置事件，換算不出知識圖譜的五項量測值（`02_目標架構.md`「對應怎麼做」），所以這一頁不用它。

- **流程**：事件 → 換算規則 **DEMO-DRAFT-0（草案，未經 PT 審核）**：行走事件信心值 0.8 以上、持續 5 秒以上、距離 3 公尺以上，步速取中位數，少於 10 次不評估 → 步行速度 0.90 m/s → 知識圖譜門檻（`kg_rules.assess`）2 分「普通」→ 居服員看的句子（`rewrite()`，目前是範本，通過輸出檢查）。
- **問答（依讀者切換）**：在地模型能力有限，所以沒有輸入框，每種讀者一組固定問題，點選提問，答完再列出延伸問題；每個回答都附依據（規則版本、知識圖譜版本、事件編號），「其他問題」一律不回答。
  - 居服員：走路狀況（`rewrite()` 正式範本）、數字怎麼算的、起身和平衡；依據預設展開。
  - 醫師：量測值與門檻原文、資料夠不夠、依據哪一版規則、哪些項目無法評估（含門檻重疊等審核用語，只給醫師）；依據預設展開。
  - 家屬：活動狀況、可以怎麼陪伴活動（知識圖譜建議原文照抄）、和上週比較（只有一週資料，無法比較）；依據預設收起。
  - 長者本人：我這週走得怎麼樣、我可以做什麼運動；依據預設收起。
  - 主管機關：照 `audience.py` 不能看個人資料，沒有題目。
  - 居服員以外的句子都標「範本草案」；題目清單與範本要經審核（單向門「給讀者的輸出與用語」）才進 `src/`。之後若開放打字提問，在地模型只把句子分類到某一題、請使用者確認，不自己產生答案。**2026-10-17**：對應的程式已做（`src/radar_agent/ask.py` 的 `match_question()`）：模型只能回一個題號，回 0、回其他文字、出錯或提問超過 100 字都當作沒對應到，改列選單；結果不留提問原文。準確率用 `radar-model-eval --questions` 量（13 題，含醫療問題與閒聊這類應該回 0 的題目），「對錯題」與「沒對應到」分開算。Demo 頁還沒接上輸入框。
- **三種狀態**：步行速度有換算規則（草案）→ 出等級；下肢肌力有坐→站事件但沒有換算規則 → 不出等級（K-1）；單腳站立、來回行走、心肺耐力雷達量不到 → 本週無法評估。另有邊界情境：中位數 0.80 m/s 落在門檻重疊，居服員只看到「目前無法評估」。
- **還缺什麼**：頁面最後一張表，對應週一清單的事件格式、K-1、K-2、K-3、4-9、4-10。
- 換算規則只寫在 `demo/kg_build.py`，不進 `src/`；審核通過後才另開 PR 做成正式規則（單向門「數字與等級的判定」）。`tests/test_kg_demo.py` 檢查頁面與產生結果一致、事件符合格式草案、等級來自知識圖譜、句子是 `rewrite()` 的輸出。

## 10/19 實測資料（2026-10-16 準備）

10/19 測試時會用真的雷達把 Demo 的每個狀況實際操演一遍（腳本與紀錄表見 `12_Demo預演.md`「10/19 實機操演」），下載有跌倒、滯留、斷線的實測資料（會議清單 A10），也會討論時區（A27）。當天照下面五步，就能用實測資料跑同一套輸出與原型頁，並逐項對照操演紀錄表。**實測資料一律不 commit、不發布到線上**。

```bash
radar-field-data inspect 下載的檔案.json                                     # 1. 檢查：格式、時間範圍、事件數、斷線、每小時有人的次數（不印出 MAC）
radar-field-data mask 下載的檔案.json --out-dir outputs/field                 # 2. 遮罩：裝置識別換成 FIELD-01…，每台一個檔案
radar-caregiver outputs/field/FIELD-01.jsonl --place "1 號廁所"               # 3. 事件摘要、處置提示、照護紀錄草稿
python demo/build.py --events outputs/field/FIELD-01.jsonl --place "1 號廁所" # 4. 實測資料版原型頁 → outputs/field_prototype.html
radar-field-data compare 操演紀錄.csv outputs/field/FIELD-01.jsonl --date 2026-10-19  # 5. 實機操演逐項比對（紀錄表用 radar-field-data sheet 產生，docs/12）
```

| 步驟 | 做什麼 | 防呆 |
|---|---|---|
| 檢查 | 看格式（JSON 陣列或一行一筆）、重複筆數、伺服器指令筆數、時間讀不懂的筆數、各事件次數（跌倒依來源分開）、超過 30 秒沒資料的段數與最長一段 | 識別碼像 MAC 時不印原值；整行壞掉就整份拒收（同 `radar-caregiver`） |
| 時區（A27） | 看「每小時有人的次數」：浴廁使用集中在 00～06 點，時間戳很可能是 UTC。確定是 UTC 時，遮罩那一步加 `--shift-hours 8` | 讀不懂的時間戳照原樣，並印出筆數 |
| 遮罩 | topic 裡的裝置識別換成 `FIELD-01`、`FIELD-02`（依第一次出現的順序）；紀錄裡其他像 MAC 的字串一律換成 `MASKED-ID`；重複紀錄照樣保留 | 只能寫到 repo 的 `outputs/`（已被 git 忽略）或 repo 以外；代號與原識別碼的對照不寫檔、不印出 |
| 原型頁 | 橫幅改成「實測資料：裝置識別已遮罩；只在本機使用」，沒有兩週趨勢 | 檔案裡還有像 MAC 的字串就拒絕產生；只寫到 `outputs/field_prototype.html`；不提供發布用的版本 |

注意：

- 遮罩後的檔案仍是場域實測紀錄，只在本機使用；Demo 時用投影或螢幕分享展示，不傳檔案。
- `radar-caregiver` 一次只整理一台裝置；實測資料有多台時，每台各跑一次。
- 實測資料跨好幾天時，處置提示與照護紀錄草稿只寫 HH:MM，沒有日期（既有限制）；原型頁的卡片會補上日期。
- 實測資料的用語如果碰到規格外的事件組合（例如 `resolved` 的 trigger 不是 noNeedHelp 或 standUp），處置提示照 G1 的規則處理，原型頁的卡片標籤要在 `demo/build.py` 的 `KINDS` 補上，否則產生頁面時會失敗。
