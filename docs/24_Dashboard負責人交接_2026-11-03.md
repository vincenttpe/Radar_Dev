## 協作方式（給 Dashboard 負責人）

本 repo（Jetson 端）暫時獨立運作：不改雷達設備、不改 Dashboard 的 repo，也還沒連真實雲端（`docs/adr/0010`）。為了將來整合，你會以協作者身分加入這個 repo。

**兩邊的接點只有兩份文件**，整合時從這裡開始：
- `docs/23_Dashboard連線API草案.md`：Jetson 向 Dashboard 取需求、取裝置事件、傳回結果的 API（草案 v0，網址、欄位名稱都可以改成你們的寫法）。
- `docs/16_Dashboard對接說明.md`：傳回的 JSON 欄位與顯示規則。

**想問問題、或想改什麼**
- 開 issue：這個 repo 的 Issues（`vincenttpe/Radar_Dev`），不是已封存的 `Deepfens-AI/Radar_Agent`。
- 改文件或程式：開分支、送 PR，照 PR 範本填寫（`.github/pull_request_template.md`）。改了 `docs/23`、`docs/16` 這兩份約定時，請在 PR 寫明 Dashboard 那邊要跟著改什麼。
- 碰到單向門的改動（給讀者的句子、個人資料的流向、事件格式等，定義見 `REVIEW.md` 第 2 節），要由 repo 擁有者核准後才合併；其他改動合併前也要經過 code-review（`CLAUDE.md`）。
- `main` 不要直接推，一律走 PR（合併前要經過 code-review，`CLAUDE.md`）。

**在自己電腦上試跑**（不連真實雲端；安裝方式見 `README.md`，必須用 `pip install -e ".[dev]"`）

## 要做的事

1. **照原文顯示文字，不要靠比對字串判斷「有沒有資料」。** 沒有資料時，現在有三種寫法：「沒有收到資料」「沒有讀得懂的資料，N 筆紀錄無法判讀」「只收到裝置斷線的紀錄（HH:MM）」。如果 Dashboard 是用「沒有收到資料」這幾個字判斷顯示方式，請改成看 report 的 `from`／`to` 是不是 `null`。（#61、#65）
2. **使用趨勢的 `days` 可能是空陣列。** 紀錄的時間全部讀不懂時，`--trend --json` 的 `days` 是 `[]`，`lines` 只有一句。這時不要畫圖，只顯示 `lines`。真的沒有紀錄時也是 `days: []`。（#65；`docs/16` 已更新）
3. **Radar60FL 的資料會寫「無法判讀」，不要當成錯誤。** Dashboard 現在下載的 Radar60FL 實測資料，報告會寫「沒有讀得懂的資料，N 筆紀錄無法判讀，無法判斷，請通知資訊人員。」，`status` 仍是 `done`。這表示格式還不支援（等 A45），不是 Jetson 壞了。（#67，issue #64）
4. **`params` 形狀不對的紀錄不會再讓工作失敗。** 以前 `payload.params` 是清單時，整份工作回 `failed`（`AttributeError`）。現在回 `done`：設定不採用、事件照常計算，報告最後一句是「另有 N 筆紀錄無法判讀，請通知資訊人員。」。（#53、#54）
5. **「無法判斷」時，數字卡先不要單獨呈現。** 摘要寫「無法判斷」時，`counts` 仍是 0（例如 `fall_alerts: 0`）。數字要不要改成 `null` 還沒決定；在決定之前，畫面上要讓摘要文字比數字卡顯眼。
6. **回答下方「要請你回答的問題」。** A45 擋住 Radar60FL 的正式支援；A49 和「records 能不能分頁」會影響 ② 取資料的做法。
7. **一起決定：沒有 Jetson 的長照中心怎麼處理。** 見「長期架構」的三個做法與功能對照，先告訴我們傾向哪一個，以及大概有多少這類機構。

- 【重點】那一行，在事件摘要的句子後面加「，請通知資訊人員。」。
- `09:00` 是斷線紀錄的時間（連續 offline 的第一筆）。不寫「之後狀況不明」，因為之前同樣沒有資料。
- 「其中」：是同一筆紀錄，不寫「另有」。還有其他讀不懂的紀錄時，後面再接「，另有 M 筆紀錄無法判讀」。

**沒有變的**
- 真的沒有收到任何紀錄時（空檔案、範圍內沒有紀錄、只有伺服器下給裝置的 `config/set` 指令），句子仍是「沒有收到資料，無法判斷。」，使用趨勢仍是「【使用趨勢】…沒有收到資料，無法判斷。」。
- 有在線時段的一般報告，寫法都沒變；有讀不懂的紀錄時，仍是「另有 N 筆紀錄無法判讀，請通知資訊人員。」。

## JSON 與工作狀態

`caregiver-report-v0`、`usage-trend-v0`、`event-ask-v0` 的欄位和格式都沒有新增或改名。變的只有下面幾種情況。

| 情況 | 以前 | 現在 | PR |
|---|---|---|---|
| 紀錄的 `payload.params` 是清單等形狀不對 | 整份工作 `failed`（`AttributeError`） | `done`；設定不採用、事件照常計算，報告寫「另有 N 筆紀錄無法判讀」 | #53、#54 |
| 紀錄全部讀不懂 | summary 寫「沒有收到資料」 | summary 寫「沒有讀得懂的資料，N 筆紀錄無法判讀…」；欄位不變 | #61 |
| 使用趨勢：時間全部讀不懂 | `days: []`，lines 是「沒有收到資料」 | `days: []`，lines 只有「沒有讀得懂的資料，N 筆紀錄時間無法判讀…」 | #65 |
| Radar60FL 紀錄 | 當成伺服器指令略過，不出現在任何地方 | 列為無法判讀，計入 N；不算心跳、不記設定變更 | #67 |
| `radar10/<裝置>/config/set` 指令 | 略過，不算心跳 | 不變 | — |

回傳結果的 `status`（③ `POST /api/v1/jetson/jobs/{job_id}/result`，`docs/23`）：

| status | 意思 | Dashboard 顯示 |
|---|---|---|
| `done` | 產生了文字。報告裡可能有「無法判讀」「無法判斷」，這不算失敗 | 照原文顯示 `result` |
| `rejected` | 文字沒通過輸出檢查，不交出任何文字；原因在 `problems` | 寫「報告沒有產生」，不要自己補字 |
| `failed` | 取資料失敗等，沒辦法產生；原因在 `problems` | 顯示報告沒有產生，不要自己補字 |

提問沒對到題目、或答案沒通過輸出檢查時，`status` 仍是 `done`：`event-ask-v0` 的 `answer` 是 `null`，原因在 `rejected`，畫面改顯示 `notice`（`docs/23`）。所以不能只看 `status` 判斷有沒有答案。

**還沒決定的兩件事**（流程確認頁列的待決）
- 摘要寫「無法判斷」時，`counts` 的數字欄位仍是 0。數字要能表示「無法判斷」（例如 `null`），屬於給讀者的輸出格式，還沒決定。
- 要求的範圍比資料長時（例如要到 12:00，資料只到 11:59:55），回傳的文字沒有寫出「之後沒有資料」，Dashboard 也分不出是沒有事件還是資料還沒到。回傳要不要附上資料到哪裡為止（例如 `data_until`），還沒決定。

## Jetson 與 Dashboard 的溝通流程

這是草案：ADR 0009 的狀態是 proposed，`docs/23` 是 v0，還沒和 Dashboard 約定，網址、欄位名稱都可以改成你們的寫法。目前本 repo 只用本機的假 Dashboard 測試，沒有連真實雲端。

方向是 **Jetson 主動往外連**：Jetson 不開任何對外埠，Dashboard 不連進 Jetson。Jetson 在機構內網、防火牆後面，這樣做不用打通道（B12）。

| 步驟 | 誰 | 呼叫 | 做什麼 |
|---|---|---|---|
| 1 | Dashboard | — | 使用者登入，依帳號鎖定機構與裝置，在佇列裡建立一筆需求：哪台裝置、哪段時間、哪種需求（`report`／`ask`／`pick`）。 |
| 2 | Jetson → Dashboard | `GET /api/v1/jetson/jobs/next` | 每 5 秒問一次。沒有回 `204`；有就回一筆，Dashboard 標成「處理中」，不再發給別台。只有這一步會帶提問原文，Jetson 不保存、不寫進 log。 |
| 3 | Jetson → Dashboard | `GET /api/v1/devices/{device}/records` | 用 `from`／`to`／`cursor` 分頁取裝置事件，回應附 `received_until` 與 `complete`。Jetson 用範本與在地模型產生文字，先通過輸出檢查。 |
| 4 | Jetson → Dashboard | `POST /api/v1/jetson/jobs/{job_id}/result` | 傳回 JSON，`status` 是 `done`／`rejected`／`failed`。Dashboard 只排版，不改字、不自己算數字。 |

- **認證與資安**：每台 Jetson 一個 token，放在 `Authorization: Bearer`，只拿得到自己機構的需求和裝置。一律 HTTPS，要驗證憑證；token 不進 repo、不寫進 log。改成每台一張憑證、用 mTLS，也是選項之一（待確認）。
- **出錯時**：Jetson 停擺時，需求留在佇列，等多久算逾時、畫面怎麼寫由 Dashboard 決定（B10）。傳回時連不上、5xx、408、429，Jetson 會補送，所以同一個 `job_id` 可能收到兩次。Dashboard 回的資料不合草案時，這筆需求回 `failed` 並寫出原因。
- **不經過這條路的**：跌倒即時警示走秒級的警示服務，Jetson 停擺也不影響（ADR 0006）；甲方週報由 Dashboard 直接從裝置事件統計（ADR 0004）。

## 長期架構（要一起確認的方向，還沒有決定）

「沒有 Jetson 的長照中心」是新的情境，repo 裡目前的前提是「每個機構現場有一台 Jetson」（ADR 0007、0009）。下面列的選項附上依據和限制，供討論用。

**現在的前提**
- 給讀者的文字由 Jetson 上的在地模型產生，不送雲端模型（ADR 0007）。日後要用雲端模型，只能送去識別的事實組合，而且要另寫 ADR 取代這一篇。
- Jetson 主動向 Dashboard 取需求（ADR 0009，proposed）。本 repo 讀的裝置事件本來就在雲端，所以 Jetson 是向 Dashboard 要資料。
- 範本層不用模型：報告、選單提問（`pick`）、使用趨勢都是固定句型。只有「打字提問」（`ask`）要用模型對題；沒有模型時，會回提示句「目前無法用打字提問，請從選單選一題。」（`notice` 已經有這一句）。

**沒有 Jetson 的長照中心：三個可能的做法**

| | A 雲端跑範本層（不用模型） | B 共用 Jetson（一台服務多個機構） | C 雲端模型 |
|---|---|---|---|
| 怎麼做 | 把本 repo 的範本層包成雲端服務，Dashboard 後台呼叫，或由一個雲端的「Jetson 角色」照同一套 API 取需求 | Jetson 放在公司機房或區域據點，照 ADR 0009 向 Dashboard 取多個機構的需求 | 文字改由雲端的語言模型產生 |
| 可以 | 報告、選單提問、使用趨勢的句子和有 Jetson 時一樣，也一樣過輸出檢查 | 功能和有 Jetson 的機構完全一樣，包括打字提問與模型改寫 | 不用任何現場或區域硬體 |
| 不行 | 打字提問（只能點選單）、在地模型改寫語氣 | 讀不到現場經 MQTT 送的雷達點雲描述句（`docs/02`：Jetson 訂閱裝置事件「需與裝置在同一個網路」，A32；跨網路是否可行待確認） | 違反 ADR 0007；只能送去識別的事實組合，要另寫 ADR，還要重新評估模型來源（ADR 0003） |
| 要決定 | 誰維運這個服務；這是「個人資料的流向」的改變，要另寫 ADR | token 與權限怎麼分機構、一台撐幾個機構（B6、B7、B11） | 是否值得推翻 ADR 0007 |

不論哪個做法，**選擇「不同步到雲端」的客戶一定要有現場 Jetson**：資料不在雲端，Dashboard 和雲端服務都拿不到（`docs/02`、A16、A17）。反過來說，這類客戶的 Jetson 也無法照 ADR 0009 向 Dashboard 取資料，要另外設計（ADR 0009「考慮過的做法」有提到，等真的有這類客戶再做）。

**功能對照**（「有」是指功能本身做得到，不代表已經實作）

| 功能 | 現場 Jetson | A 雲端範本層 | B 共用 Jetson | C 雲端模型 |
|---|---|---|---|---|
| 報告（【重點】、事件摘要、交班重點） | 有 | 有 | 有 | 有 |
| 選單提問（pick） | 有 | 有 | 有 | 有 |
| 打字提問（ask） | 有 | 沒有 | 有 | 要另寫 ADR |
| 在地模型改寫語氣 | 有 | 沒有 | 有 | 要另寫 ADR |
| 知識圖譜等級（規則引擎） | 有 | 有 | 有 | 有 |
| 現場雷達點雲描述句（radarLLM） | 有 | 沒有 | 沒有 | 沒有 |
| 不同步到雲端的客戶 | 可以 | 不行 | 不行 | 不行 |

知識圖譜的等級由明文規則和門檻決定，不經過模型（`docs/02` 原則 2），所以四種做法都能做。

**Jetson 的長期角色**
1. **產生報告文字**：範本產生事實句，在地模型只改語氣，輸出檢查把關數字與用語，沒過就退回範本。這就是現在 Dashboard 接的這條路。
2. **導入知識圖譜**：把審核核准的知識圖譜版本帶上 Jetson（`kg/releases.json` 記雜湊與核准狀態），由規則引擎把量測值換算成等級和建議。每份輸出都記下用了哪一版、是否已核准；未核准的版本，輸出一律標「僅供測試」。知識圖譜只存知識，不存個人資料；更新要人審核，不自動更新。
3. **現場資料的落腳處**：現場經 MQTT 收雷達點雲、轉成描述句（radarLLM）。對不同步到雲端的客戶，Jetson 是唯一保存資料的地方，備份方式待定（A16）。

知識圖譜導入後，Dashboard 會多一種要顯示的內容：個人的指標等級、建議，以及知識圖譜版本。這需要特定個人的量測，例如起站次數、步行速度；目前的廁所資料沒有個人 ID，Demo 是用人工輸入的量測值示範。

**API 與部署**（`docs/23`「要和 Dashboard 負責人確認」）

11. 權限只在 Dashboard 控管、Jetson 完全信任送來的需求，可以嗎？
12. 同一個 `job_id` 的結果可能收到兩次（第一次其實送到了，只是回應沒傳回來）。Dashboard 收到重複的結果能不出錯嗎？以最後一次為準或忽略都可以。
