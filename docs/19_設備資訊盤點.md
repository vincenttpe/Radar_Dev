# 設備資訊盤點：控制端要掌握哪些設備資訊（討論稿）

**狀態**：討論稿（2026-10-23）。給軟硬體團隊、雷達廠商與雲端負責人討論用；「必要程度」是產品設計建議，不是已確認的規格。缺的項目已列成會議追問（`docs/05` A35–A44、D5–D6）。

## 一、為什麼要盤點

目前每份資料只確定有裝置 MAC 與韌體版本（`docs/05` A5、A28）。要讓系統完整、出問題時追得回來，控制端（雲端 Server）要能回答五件事：

1. 這台設備**是誰**（身分，不只是 MAC）。
2. **在哪裡**（場域、位置、安裝方式）。
3. **是否正常工作**：連線、感測與判定、告警送達，三件事分開看。
4. **目前實際跑什麼**：韌體、判定規則或模型、設定，而且分「目標」與「實際」。
5. **下達的指令是否真的完成**：重啟、更新、改設定都要有執行結果，不是送出就算數。

Reset 這類動作屬於「遠端操作」，要另外記錄指令、原因、結果與時間，不是設備資料裡的一個欄位（第四節）。

## 二、前提：誰負責哪一段

| 範圍 | 負責 | 依據 |
|---|---|---|
| 設備管理、遠端操作、跌倒即時警示 | 雷達廠商與雲端 | ADR 0006：警示不經過本 repo |
| 分析路徑：事件摘要、處置提示、各讀者的報告 | 本 repo（Jetson） | `docs/02`、ADR 0007 |
| 安裝地點、場域與長者對照 | 機構（與雲端） | `docs/05` A15、`docs/17`「裝置設定紀錄」 |

所以這份清單多數項目是要**廠商或雲端提供、或回答**的；本 repo 自己要做的只有第六節的版本追溯。另外兩條限制：

- ADR 0005：不接收音訊資料。語音相關只能拿自檢結果、服務狀態等資訊，不拿音訊本身。
- ADR 0008：非醫療器材。設備健康狀態的用語一樣不用醫療用語。

## 三、盤點表

「現況」欄：**有**＝現有資料已經有；**部分**＝有線索但不完整；**試做**＝只在看板試做頁用模擬資料示意；**沒有**＝目前拿不到。

| 類別 | 建議資訊 | 必要程度 | 現況 | 歸屬 | 對應題號 |
|---|---|---|---|---|---|
| 設備身分 | 平台內的設備 ID、序號、型號、硬體版本 | 必備 | 部分：只有 MAC（在 MQTT topic 裡） | 廠商 | A5、A35 |
| 網路介面 | 各介面的 MAC、連線類型、IP、經過的閘道器 | 依介面必備 | 部分：只有一個 MAC | 廠商 | A35 |
| 所屬與位置 | 客戶／租戶、場域、樓層、房間、安裝日期 | 必備 | 試做：設定紀錄（地點、區域、用途、異動） | 機構＋雲端 | A15、A41 |
| 安裝與校正 | 安裝高度、角度、偵測區域、排除區域、校正版本與時間 | 毫米波必備 | 沒有 | 廠商＋機構 | A41 |
| 連線狀態 | 最後連線、最後心跳、預期回報週期、在線判定 | 必備 | 有：online／offline（broker 依 keepalive 發送）；回報週期用實測的約 5 秒 | 廠商 | A29、D3 |
| 系統運作 | 開機時間、Uptime、Boot ID、最後重啟原因、錯誤碼 | 必備 | 部分：只有 error 訊息 `radar is not running` | 廠商 | A36、A37 |
| 資源與供電 | CPU、記憶體、儲存、溫度、供電狀態 | 依硬體支援 | 沒有 | 廠商 | A43 |
| 軟體與韌體 | 韌體、應用程式、OS／Bootloader、Build ID | 必備 | 部分：韌體在 online 訊息裡，欄位名稱待確認；目前要另外送一則固定的 MQTT 訊息，裝置才會回報 MAC 與韌體版本 | 廠商 | A5、A28 |
| 設定 | 設定版本、目標設定、實際設定、支援的功能 | 必備 | 部分：裝置送的設定訊息（`fallSwitch`、`fallSensitiveLevel` 等）只是實際狀態 | 廠商＋雲端 | A26、A31、A38 |
| 感測器健康 | 初始化與自檢結果、最後有效感測時間 | 感測設備必備 | 部分：只能從「有沒有資料、能不能判讀」間接推 | 廠商 | A39 |
| 語音健康 | 麥克風／喇叭自檢、語音服務狀態、互動成功或失敗原因 | 有語音確認必備 | 沒有 | 廠商 | A39 |
| 裝置端判定 | 跌倒／久待判定的規則或模型版本；每個事件由哪個版本產生 | 必備 | 沒有 | 廠商 | A40 |
| 遠端操作 | 指令 ID、類型、參數、執行階段、結果、失敗原因、時間 | 有遠端控制必備 | 沒有（看板的「回報問題」是回報單，不是控制） | 雲端 | A42 |
| 資安與生命週期 | 驗證方式、憑證到期日、啟用／停用／撤銷、支援期限 | 必備 | 沒有 | 廠商＋雲端 | A44 |
| 操作稽核 | 誰、何時、對哪台設備、做了什麼、結果 | 必備 | 試做：設定紀錄的變更人與時間 | 雲端；正式版後端見 #76 | A42 |
| 告警送達 | 告警是否進入通知流程、是否送達、有沒有人確認、是否升級 | 照護必備 | 沒有（不經過本 repo） | 雲端 | D5 |
| 斷網處理 | 本地告警能力、待補傳事件數、補傳結果 | 照護必備 | 部分：知道斷線時段，不知道有沒有補傳 | 廠商 | D3、D6 |

### MAC 要保存，但不當唯一主鍵

- **設備 ID**：平台內固定不變的識別。
- **序號**：製造、維修與實體標籤用。
- **網路介面清單**：每個介面的 MAC、IP。
- **驗證**：用憑證或金鑰確認「連進來的是不是那台設備」，不是只比對 MAC。

另外，MAC 在一戶一台的場域等於可以認出是誰（`docs/05` F10），對外報表與回報單一律換成代號。

## 四、遠端操作：Reset 要拆開

不建議只放一個意思不清楚的「Reset」。建議分成：

| 操作 | 要先講清楚的事 |
|---|---|
| 重啟偵測服務 | 只重啟偵測或推論服務，不重開整台設備 |
| 重開設備 | 重開後保留設定與設備身分 |
| 重設部分設定 | 清掉哪些設定？網路與憑證保不保留？ |
| 恢復原廠設定 | 清除範圍、平台綁定怎麼處理、怎麼重新註冊；要限制權限並二次確認 |
| 韌體更新 | 目標版本、相容性、來源與完整性驗證、失敗怎麼回復 |
| 判定規則或模型更新 | 版本、相依的韌體、驗證與回復方式 |
| 收集診斷資料 | 指定時間區間的紀錄、自檢與錯誤資訊 |
| 更換憑證 | 換完確認新憑證能連線 |

每次操作都當成一個**可追蹤的任務**：建立 → 等待設備接收 → 已接收 → 執行中 → 成功／失敗／逾時。至少記錄：指令 ID、設備 ID、操作類型、參數、誰下的、下達時間、有效期限、執行狀態、錯誤碼、完成時間。

重點：**送出成功不等於執行成功**，要等設備回報。重開設備後還要確認新的 Boot ID、開機時間與健康檢查，確定不只是重新連線，偵測也恢復了。

更新或重開期間偵測會中斷，要事先通知誰、什麼時候恢復，也要記錄下來；照護場域裡這段時間等同斷線（看板寫「無法判斷」）。

## 五、目標狀態與實際狀態分開

| 狀態 | 誰提供 | 例子 |
|---|---|---|
| 目標狀態 | 雲端（管理者設定） | 希望用韌體 1.3、跌倒靈敏度 3 |
| 實際狀態 | 設備回報 | 目前韌體 1.2、靈敏度 2 |
| 同步狀態 | 設備回報、雲端彙整 | 下載中、套用失敗、設備離線還沒收到 |

這樣才答得出：設定是不是真的套用了？哪些設備還沒升級？是離線還是更新失敗？畫面上看到的是實際狀態還是管理者想要的狀態？

`docs/05` A31（`fallSwitch` 為 false 時以誰為準）卡住，就是因為目前只看得到實際狀態。

**時間戳**：狀態要附「設備回報的時間」；感測資料另外分「事件發生時間」與「Server 收到的時間」。目前只知道裝置事件的時間以雲端服務的時區為準，時區與是否分開記錄都還沒確認（`docs/05` A27）；事件編號也是雲端收到時才給的（A5）。離線後看到的只能叫「最後已知狀態」，不能繼續顯示成即時正常。

## 六、本 repo 自己要做的：每一筆輸出追得回來

依原則 3「每一筆都追得回來」，本 repo 產生的報告、照護紀錄草稿與提問答案，要記錄是哪些版本產生的：

| 版本 | 現況 |
|---|---|
| 裝置端判定規則或模型 | 要等廠商回答 A40 |
| 韌體 | 要等 A28 的欄位名稱 |
| radarLLM（Jetson 上的描述句） | 待確認版本號從哪裡取 |
| 在地模型與 prompt | 本 repo 可控，待補 |
| 知識圖譜與句庫 | 已有版本與核准紀錄（`kg/`、ADR 0002） |

前三項拿到之後，再另開 issue 把版本寫進每一筆輸出。

## 七、看板要怎麼呈現（等回答之後）

「設備連線」「偵測服務」「告警通道」三種健康狀態分開顯示，不要合成一個綠色「在線」：

- **設備連線**：現在已有（online／offline、資料逾時）。
- **偵測服務**：現有線索是 error 訊息 `radar is not running`（在線但沒有在偵測）；A39 回答後可以補自檢結果。
- **告警通道**：本 repo 拿不到，要等 D5；拿到之前畫面寫「資料未提供」。

遠端操作（重開、更新等）屬於廠商雲端，看板試做頁先不加，免得看起來像本系統能控制設備。

## 八、第一版最小規格（給廠商與雲端參考）

| 模組 | 內容 | 歸屬 |
|---|---|---|
| 設備註冊 | 設備 ID、序號、型號、硬體版本、驗證身分、場域綁定 | 廠商＋雲端 |
| 心跳回報 | 時間、Boot ID、Uptime、系統／感測／判定的健康狀態、錯誤碼 | 廠商 |
| 版本回報 | 韌體、應用、判定規則或模型、設定版本 | 廠商 |
| 設定同步 | 目標與實際設定、設定版本、套用結果 | 廠商＋雲端 |
| 遠端任務 | 指令 ID、有效期限、執行回報、稽核紀錄 | 雲端 |
| 安全更新 | 來源與完整性驗證、失敗復原、更新後健康檢查 | 廠商 |
| 事件告警 | 事件 ID、時間、嚴重程度、通知與處理狀態 | 雲端 |

每個欄位定案時，再補五項定義才算可以驗收的通訊規格：

| 欄位 | 資料型別 | 來源 | 回報時機 | 過期判定 | 讀寫權限 |
|---|---|---|---|---|---|
| 例：最後重啟原因 | 列舉（斷電、Watchdog、遠端重開、更新…） | 設備 | 每次開機後的第一則 online | 下次開機前都有效 | 設備寫；雲端、系統管理人員讀 |
| 例：跌倒靈敏度（目標） | 整數 1–5 | 雲端 | 管理者修改時 | 不過期，直到再修改 | 系統管理人員寫；設備讀 |

## 九、要團隊決定的事

1. 第三節「必要程度」要不要調整？哪些是第一版就要、哪些可以之後再補？
2. 設備 ID 由誰發、格式是什麼（和 MAC、序號的關係）？
3. 「偵測服務」與「告警通道」的健康狀態，雲端願不願意提供給本 repo 或 Dashboard？
4. 遠端操作的權限：誰可以重開、誰可以恢復原廠？要不要二次確認？
5. 正式版的設定紀錄與操作稽核放在哪裡（接續 #76 與 `docs/17`「設定紀錄由誰維護」）。
