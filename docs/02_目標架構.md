# 目標架構（草案，待團隊確認）

## 本 repo 的範圍（2026-10-08 確認）

現有系統已經保存最近 7 天內的全部雷達資訊，目前只做簡單運用。本 repo 是從這個現況分出來的新分支，負責分析建議路徑中「知識圖譜對應」到「輸出文字」這一段：

1. 讀取 7 天雷達資訊。來源有兩條（2026-10-08 雷達負責人說明）：雲端保存的資料，或邊緣裝置經 MQTT 直接送到 Jetson PC 的同一份資料。Jetson PC 同時是本 repo 的輸出伺服器（跑在地 LLM，待確認事項第 5 項）。
   - **2026-10-12 確認**：Jetson PC 視為現場的小型私有雲。裝置直接把動作狀態 JSON（現場稱為 Raw data，指裝置已判定好的狀態，不是雷達原始 `.bin`）送到 Jetson，Jetson 與知識圖譜比對後，由在地 LLM 產生文字或語音報告。mmWave 取得的資訊**預設全部同步到雲端，客戶要求時不同步**；不同步的客戶，Jetson 就是唯一保存資料的地方（備份方式與「客戶」以誰為單位，見會議清單 A16、A17）。本 repo 只用「動作狀態 JSON」（moving、longstay、vacant、fall 等），不碰雷達原始 `.bin` 與音訊 `.bin`；完整欄位待確認（待確認事項第 1 項）。
   - **音訊 `.bin` 含長者語音**，屬個人資料。本 repo 不接收、不保存、不處理；它在雲端與 Jetson PC 上的保存期限、存取權限與刪除，由現有系統負責（2026-10-08 公司確認）。本 repo 若在 Jetson 上與這些檔案共用機器，程式不得讀取該目錄。
2. 以明文規則把資訊換算成知識圖譜各指標的量測值，再查門檻得到等級；在地模型不決定等級（細節見下方「對應怎麼做」）。
3. 依不同 Profile 輸出各自需要的文字訊息：狀態、建議等；也可能輸出語音報告（2026-10-12，讀者與合成位置見會議清單 F8）。Profile 先按下表五種規劃（2026-10-08 確認），內容細節待甲方與各讀者確認。

| Profile | 要看什麼 | 用語 |
|---|---|---|
| 居服員（**先做**，2026-10-12 決定） | 每位長者近 7 天的狀態摘要、需注意的變化、今天可帶的活動；事件摘要、處置提示與照護紀錄草稿（`08_KPI與查核點.md`） | 口語、可直接照做 |
| 醫師 | 各指標等級與 7 天趨勢、對應的知識圖譜依據與版本 | 專業用語、附數值 |
| 家屬 | 整體狀況、有沒有變差、在家可以怎麼陪伴 | 白話、避免嚇人也不淡化 |
| 長者本人 | 自己的狀況與鼓勵、今天建議做的運動 | 簡短、正向、國語或台語 |
| 主管機關 | 機構層級的統計與趨勢，不含個人資料 | 報表格式、去識別 |

同一份事實（等級、建議）只產生一次，五種 Profile 只是改寫與取捨，不會各自得到不同的等級。

**甲方週報由 Dashboard 處理（2026-10-12 決定）**：甲方要看每週的跌倒次數與活動量（2026-10-08 確認），這兩個數字直接從動作狀態 JSON 統計，不需要知識圖譜，改由 Dashboard 從雲端或 Jetson 的資料計算，本 repo 不產生週報。本 repo 曾做過週報第 1 版，已移除；當時定下的統計規則與踩過的問題整理在 `07_週報交接_Dashboard.md`。本 repo 交給 Dashboard 的是知識圖譜的等級判定，以及各 Profile 的文字或語音報告。

雷達偵測、跌倒警示、7 天資料的保存都在現有系統，不在本 repo 範圍；本 repo 只讀資料、不改上游。

## 輸出的對象：場域與個人（2026-10-12 確認）

同一套架構要同時用在兩種場域：

| 場域 | 個人 ID | 能產生的輸出 |
|---|---|---|
| Demo：機構的廁所（多人使用） | 沒有 | 場域層級：給居服員看這個地點近期的狀態與需注意的事件（跌倒、久待），給主管機關看場域統計 |
| 老人公寓（2026-10-12：可設定個人 ID） | 可設定 | 場域層級之外，加上個人層級：家屬、長者本人、醫師的報告，個人基線與趨勢 |

規則：

- **每份輸出記下對象是「場域」還是「個人」。** 場域以裝置（MAC）與地點表示；個人以 `subject_id` 表示（事件格式草案中本來就是選填）。
- **沒有 ID 不推測是誰。** 多人場域的跌倒只能說「這個地點有人跌倒」，不能依時間、習慣猜是哪一位長者。
- **個人基線、趨勢、家屬報告只用有 ID 的資料。** 同一套程式在設定 ID 的場域產生個人報告，不另寫一套。
- **沒有 ID 也視同個人資料。** 如廁次數與停留時間本身就敏感，小型機構裡從時間與地點也可能認出是誰，一樣適用個人資料的保護（`REVIEW.md` 3.3）。
- **知識圖譜的體能指標**（來回行走、單腳站立等）需要特定個人的量測。Demo 的廁所資料沒有 ID、也沒有測驗，所以 Demo 的知識圖譜部分以人工輸入量測值示範，並標明不是來自廁所的資料。

待確認：老人公寓的 ID 怎麼設定與綁定、公共空間是否沒有 ID（會議清單 A5）；裝置能否分出多人（A18）；多人場域跌倒時通知誰（D4）。

## 長期目標：感測資料與知識圖譜結合的資料庫（方向，2026-10-12）

最終目的是把感測資料與知識圖譜結合，累積成有價值的資料庫，成為智慧醫療系統的重要角色之一。資料庫的價值取決於資料存下來時記了什麼，事後很難補，所以從現在起每一筆資料都要能回答：

| 要能回答 | 做法 | 目前狀態 |
|---|---|---|
| 是誰的、在哪裡 | 記下對象是場域還是個人（上一節）；沒有 ID 不推測 | 原則已定；`subject_id` 已在事件格式草案 |
| 數字從哪來、準不準 | 記下裝置、韌體版本、換算規則版本與信心值 | 每筆資料都有 MAC 與韌體版本（2026-10-12 確認），但本 repo 能否取得待 A5；信心值待 A7 |
| 為什麼得到這個等級 | 記下知識圖譜版本、是否已核准、對到哪一級 | `radar-kg-level` 已這樣輸出 |
| 哪裡缺、哪裡不確定 | 在線時段、無法判讀的筆數、補傳紀錄 | 原則見「子機斷線與資料補傳」；在線時段待 D3 |
| 能不能拿來研究或分享 | 同意範圍、去識別、使用範圍 | 待確認第 8 項（公司負責）；會議清單 F9、F10 |

- **MAC 在老人公寓等於可識別個人**：一戶一台裝置時，MAC 固定對應一位長者。營運用的資料（Jetson、雲端）照常保存 MAC；進研究用或交給第三方的資料庫時，MAC 要換成無法反推的代號（F10）。
- **與定位的關係**：本系統目前定位為非醫療器材軟體（待確認第 9 項）。成為智慧醫療系統的一環後，資料或建議若用於臨床判斷，定位可能要重新評估（F11），由公司決定。

## 三個原則

1. **兩條路分開。** 跌倒警示走秒級的即時路徑，不經過知識圖譜、LLM 或報表伺服器；其他姿態判斷走分析路徑，產出各 Profile 的報告（週報由 Dashboard 統計）。分析路徑故障不影響警示。
2. **事實在上游決定。** 數值、分數、建議由規則與知識圖譜決定；在地 LLM 只負責依讀者改寫說法，不能新增或改動事實。對尚無規則的指標，在地模型可以提出「候選等級＋理由」，但候選只進審核佇列，不進任何輸出（2026-10-08 確認採此走法）。
3. **每一筆都追得回來。** 同一個事件編號從雷達一路帶到 Dashboard，每一步記時間戳；每份輸出記下用了哪一版規則、知識圖譜與 Profile。

## 資料流

**即時警示路徑（只處理跌倒）**

雷達偵測 → 裝置判定跌倒 → 立即送出預警（斷網時本地警報）→ 裝置端語音確認（國語、台語、英語關鍵詞；有限語句，不經雲端下指令；等 10 秒、重問一次）→ 結果送雲端伺服器 → 雲端伺服器通知：沒回應先通知居服員（含備援）→ 升級或取消 → 居服員、家屬、機構按「已收到」，逾時自動升級

端到端延遲目標 2–3 秒（待確認事項第 3 項，2026-10-08 部分確認）。這是內部目標；結案驗收的是「系統緊急通報時間 < 10 秒」（事件發生到護理人員接獲通知，`08_KPI與查核點.md` KPI 3）。

**分析建議路徑（全部姿態）**

動作狀態 JSON（雲端 HTTPS 取得，或邊緣裝置 MQTT 直送 Jetson PC）→ 事件佇列（斷線暫存補傳）→ 格式檢查、去重、原始存檔 → 個人時序資料庫（以代號存）→ 規則評分（常模＋個人基線）→ 知識圖譜取建議 → 在地 LLM 依 Profile 改寫（失敗時改用範本）→ 輸出檢查（數字、用語、權限）→ Dashboard 與報表 → 現場回饋（誤報／屬實）→ 知識圖譜更新審核、去識別研究庫

## 對應怎麼做（2026-10-08 確認：規則對應，模型受控）

知識圖譜 v1 的等級是用量測值定義的（起站 30 秒次數、單腳站立秒數、2.44 公尺來回秒數、2 分鐘抬腳次數、步行速度 m/s），雷達給的是姿態與動作事件加時間戳，所以「對應」分兩段：

1. **雷達事件 → 指標量測值或替代量**：明文規則與統計，例如由 7 天內的坐→站事件算完成時間與次數、由行走事件算平均步速。規則有版本號，PT 或公司審核後才啟用。
2. **量測值 → 等級**：查知識圖譜該版本的門檻。

依指標目前的狀態分三種處理：

| 指標狀態 | 等級由誰決定 | 在地模型做什麼 | 進輸出？ |
|---|---|---|---|
| 已有換算規則 | 規則＋知識圖譜門檻 | 只把等級與建議改寫成各 Profile 的語氣；失敗時用範本 | 是 |
| 尚無規則 | 不出等級 | 可依資料提出「候選等級＋理由」，進審核佇列；審核人若認可，歸納成規則，下次由規則出 | 否，只到審核佇列 |
| 雷達量不到 | 不出等級 | 不做 | 輸出明寫「本週無法評估」 |

每個正式輸出的等級都要能回答：依據哪一版規則、哪一版門檻、哪幾筆事件編號。模型的候選同樣記錄輸入摘要與輸出，供審核人比對。

**硬體前提**：評估初期不會有高階伺服器，在地模型以小型模型（例如 Qwen2.5 0.5B–3B 等級）為準。這也是不讓模型決定等級的原因之一：小模型對數字推理不可靠，改寫與整理候選是它能勝任的事。

## 在地模型負載與分流（草案，2026-10-11 提出，待確認）

在地模型的負載只來自分析建議路徑：跌倒警示不經過模型（原則 1），等級由規則決定（原則 2）。模型只做兩件事：依 Profile 改寫同一份事實（主要負載，約為「長者人數 × Profile 數 × 報告頻率」），以及對尚無規則的指標提出候選等級（量少，只進審核佇列）。這些多半是批次工作，可以排程、預先算、重複使用。

依「越前面越便宜、越後面越少」分層，每一層只處理前面攔不下的部分：

| 層 | 處理什麼 | 做法 |
|---|---|---|
| 規則與範本 | 「本週無法評估」、等級沒變化、主管機關報表等固定句型 | 範本是主要路徑，不只是模型失敗時的備援；個人資訊（姓名等）一律以範本欄位填入 |
| 快取 | 等級組合相同的長者 | 以「等級組合＋建議＋Profile＋知識圖譜版本」為鍵，同一組合只改寫一次；鍵不含個人資料 |
| 在地小模型 | 有變化、快取沒有的改寫 | 輸入結構化事實、限制輸出長度，之後一律經輸出檢查；夜間批次產生，排隊或超時就改用範本 |
| 人工審核 | 候選等級、模型輸出沒通過檢查的 | 兜底是審核佇列，不是更大的模型；若日後考慮雲端模型，只能送去識別的事實組合，需另行決策 |

為了日後換模型、加機器時不必改報告程式，現在就要留的接口：

- **統一的改寫介面**：範本、快取、模型都實作同一介面，路由規則集中一處。
- **追溯紀錄加上「走哪一層」**：延續原則 3，每段文字記下來自範本、快取還是哪一版模型。
- **Jetson 資源隔離**：Jetson 同時接收 MQTT 資料，批次推論不能拖慢接收（行程優先順序、限制同時推論數）。
- **量測**：記錄各層每天的處理量、模型延遲與 token 數，用實際數字估算一台 Jetson 撐得住多少位長者。

規模與多台 Jetson 怎麼分工、彼此怎麼連接，見會議清單 B6～B10。硬體型號怎麼評估，見 `06_Jetson硬體評估.md`。

## 子機斷線與資料補傳（草案，2026-10-11 提出，待確認）

子機（邊緣裝置）的暫存與補傳屬於現有系統，本 repo 不實作；但補傳怎麼做，決定了本 repo 的報告能不能分辨「長者沒動」和「資料沒到」。分兩段：

**上游（現有系統）需要具備的**，對應會議清單 A13、A14、D3：

- **斷線本身就是安全事件**：子機斷線期間長者沒有被監測，跌倒也不會即時通知。警示服務要靠裝置心跳偵測斷線，斷線超過門檻就通知居服員，不能只等補傳。
- **跌倒在斷線時**：裝置已有本地警報；補傳時跌倒事件優先送、不能因暫存空間滿而被丟棄。
- **本地暫存**：斷電後仍保留（寫入快閃記憶體，不只放在記憶體），容量要能撐過預期的最長斷線時間；滿了的時候先丟哪一種事件要明文規定。
- **補傳帶原始時間與序號**：時間戳是事件發生時間，不是補傳時間；斷線期間裝置時鐘會飄，連線後要校時並記下誤差。每台裝置的事件序號連續，接收端用來去重與找出缺口（與 A11 相同）。
- **兩條路互為備援**：雲端 HTTPS 與 MQTT 直送 Jetson 是同一份資料，其中一條斷了另一條可以補，但兩邊要能比對出同一筆（同樣靠裝置編號＋序號）。客戶要求不同步到雲端時沒有這層備援，Jetson 故障或遺失就沒有第二份資料（會議清單 A16）。

**本 repo 要配合的**：

- **涵蓋率**：除了事件，也要拿到裝置在線／離線的時段。報告遵守「沒有資料不等於沒有跌倒」的原則；有了在線時段，才能逐日標出「這天只有 N 小時有資料」，活動量偏低時不會誤判成長者動得少。
- **晚到的資料**：週結束後才補傳進來的事件，要嘛等到截止時間才產生報告，要嘛先出報告、補傳後重新產生並標明版本與差異。採哪一種待會議清單 C6 決定；兩種都不能悄悄改掉已送出的數字。
- **去重與只追加**：接收端以裝置編號＋序號去重，原始事件只追加不修改；同一份資料重送多次，算出來的報告要一模一樣。
- **超過 7 天保存期的斷線**：現有系統只保存最近 7 天，斷線超過暫存容量或 7 天的資料可能永久遺失；報告要寫明缺口，不推估補值。

## 知識圖譜的更新來源（2026-10-08 確認）

知識圖譜不是一次建好就不動，預期從多個方向更新，但因為內容與醫療行為相關，**不做全自動更新**：每一條變更都由人審核後才進版（審核人見待確認事項第 6 項）。

| 來源 | 方式 |
|---|---|
| 學術資料 | 把文獻的量表、常模、建議重新編碼成知識圖譜的指標、等級與建議 |
| 實際數據 | 現有系統累積的雷達資訊與現場回饋，用來檢視門檻、等級與建議是否合理，提出修改候選 |
| 現有 v1 | 舊雛形承接的 5 個指標，作為起點 |

無論來源，流程都是「提出候選 → 人審核 → 升版（v2、v3…）→ 舊版保留」。程式可以協助整理候選與比對差異，但不能自行寫入知識圖譜。

## 各元件職責

| 元件 | 職責 |
|---|---|
| 裝置（雷達＋小型語言模型） | 偵測姿態與跌倒；用語音向長者確認；只送結構化事件，不送文字或語音 |
| 警示服務（雲端伺服器） | 接收裝置的跌倒預警與語音確認結果，多通道通知（沒回應先通知居服員），追蹤「已收到」與逾時升級，監看裝置心跳 |
| 事件接收 | 格式檢查、去重、原始事件只追加不修改 |
| 評分 | 規則門檻對應知識圖譜的評分標準；記錄規則與圖譜版本 |
| 知識圖譜 | 只存知識（指標、等級、建議），不存個人資料；更新需審核（目前由公司審核，見待確認事項第 6 項） |
| 報告 | 組裝建議、依讀者 Profile 改寫、輸出前檢查 |
| Dashboard | 呈現警示、報告與甲方統計；收集現場回饋 |
