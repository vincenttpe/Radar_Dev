# Jetson 硬體評估方式（草案，2026-10-11）

目的：用可重現的量測決定 Jetson 型號，而不是看規格表的 TOPS 挑。選好型號之後怎麼把本 repo 裝上去，見 `20_Jetson部署流程.md`。規格與數字以 NVIDIA 官方資料為準，下方引用的是 2026-10 查到的公開數據，採購前要再核對。

## 1. 先列出 Jetson 上要跑什麼

| 工作 | 吃什麼資源 | 備註 |
|---|---|---|
| 在地 LLM（Profile 改寫、候選等級、提問對應） | GPU、記憶體頻寬、記憶體容量 | **主要負載**，決定型號。2026-10-17 起等級與建議的句子改為查句庫（`docs/adr/0002`），這部分不耗模型；照護紀錄改寫、綜合摘要、提問對應仍在 Jetson 上跑 |
| MQTT 接收與事件存檔 | CPU、磁碟寫入 | 量小但不能被推論拖慢（`02_目標架構.md`「在地模型負載與分流」） |
| 規則引擎 | CPU | 很輕 |
| Neo4j（若放本機，B3） | 記憶體（JVM heap）、磁碟 | 會和模型搶記憶體 |
| 其他現有服務、音訊檔接收（B2） | 未知 | 待會議確認 |

Jetson 的 CPU 與 GPU **共用同一塊記憶體**，模型、Neo4j、作業系統要一起算。

## 2. 估算需求

**記憶體**

```
模型權重 ≈ 參數量 × 量化位元數 ÷ 8      （3B、4-bit ≈ 1.5–2 GB）
＋ KV cache（隨上下文長度與同時處理數增加）
＋ 作業系統與 CUDA 執行環境（約 1.5–2 GB）
＋ Neo4j、MQTT、其他服務
× 1.3 預留
```

**推論時間**

```
每天模型呼叫數 ＝ 需要模型改寫的「事實組合」數 × Profile 數      （範本、快取攔下的不算）
每天 GPU 時間 ≈ 呼叫數 ×（輸入 token ÷ prefill 速度 ＋ 輸出 token ÷ decode 速度）
```

要能在批次時段內（例如夜間 4 小時）跑完，且只用到一半，留給重跑與成長。

**粗估範例**（假設值，只示範算法）：50 位長者 × 4 個個人 Profile × 每天一次 ＝ 200 次；每次輸出 300 token ＝ 每天 6 萬 token。以 20 token/s 計約 50 分鐘，這還是完全沒有快取的情況。小規模時入門機種可能就夠；規模由 B6、B10 的答案決定。

decode 速度主要受**記憶體頻寬**限制（每產生一個 token 要把權重讀一遍），理論上限約為「頻寬 ÷ 權重大小」，實測通常只有一半左右。

## 4. 實測步驟

先買一台入門開發套件（Orin Nano Super 開發套件約 249 美元）做量測，再決定量產型號。

1. **準備真實工作**：用 Profile 改寫的實際 prompt（結構化事實＋範本指示），不要用通用測試題。**2026-10-17 已備妥**：`radar-model-eval` 內建 20 題（裝置事件 11 題、知識圖譜等級 9 題，全部是程式產生的模擬資料），每題走正式的 `rewrite()`，量採用率、每題延遲、token／秒，並統計退回原因。接法有三種：`--endpoint`（OpenAI 相容 API，例如 llama.cpp server、Ollama）、`--cmd`（任意指令，prompt 從標準輸入送入）、`--echo`（照抄原文的假模型，試跑用）。

   ```bash
   radar-model-eval --endpoint http://127.0.0.1:8080/v1 --model gemma4-e4b-q4_k_m
   radar-model-eval --endpoint http://127.0.0.1:11434/v1 --model llama3.2:3b --show   # 印出被採用的輸出，給人看品質
   ```

   題組裡知識圖譜的建議原文（例如 K2 的「由醫師或物理治療師評估」）照規則必須一字不改；這段原文是否合乎非醫療器材的用語，待知識圖譜審核（E4～E6）。
2. **候選模型**：Llama3-TAIDE-LX-8B、Llama 3.2 1B／3B、Gemma 3 1B／4B、Gemma 4 E2B／E4B、Gemma-3-TAIDE-12B-Chat 等（清單與理由見 `docs/adr/0003`，含 2026-10-27 的候選更新；Llama-Breeze2 已排除），各試 4-bit 與 8-bit 量化；每個候選都要記下開發者、base model 與授權（F2）。中國開發、以其為基底或含有中國開發部分的模型不用，`radar-model-eval` 也會依名稱擋下。
3. **量測項目**：
   - prefill 與 decode 的 token/s；
   - 記憶體峰值（`tegrastats`）；
   - 功耗與溫度，**連續跑 1 小時以上**，看會不會因過熱降頻（NVIDIA 的數據也提到降頻影響）；
   - 同時灌 MQTT 事件，確認接收延遲不受推論影響。
4. **品質**：每個模型的輸出都經過輸出檢查（數字、用語、權限），算通過率；台語輸出另外請人看。**先找通過品質門檻的最小模型，再看速度。**
5. **記錄**：JetPack 版本、電源模式、量化方式、推論框架，結果才能重現與比較。

**怎麼判斷夠不夠用（暫定，Demo 前再確認）**

- **固定題組（`--event-questions`、`--demo-questions`）的對錯題要是 0**（2026-11-04 決定，PR #79）。對錯題比沒對應到嚴重：照護人員沒看清楚就按「是」，會拿到別題的答案。沒對應到時會改列選單，不影響回答。
- **新問法靠確認步驟把關**：有限的題目證明不了所有問法都不會對錯，`--scope-questions` 不要求歸零，用來看對錯題有沒有變多；發現漏網的問法就收進題組。
- 「他今天血壓多少」這類不該對應的題目（V13～V15、V30～V35：醫療判斷、閒聊、要模型寫文字，以及還不支援的追問），要回 0（沒對應到）。
- 正確率暫定 80% 以上。不夠的話，先改題目文字或提示，再考慮換模型。
- 合併 2026-10-28 的兩次補題後共 35 題（V1～V35；V24、V25 同日改成「有哪些警報要處理」「上了幾次廁所」，原本的「警報」「幾次」在 longstay 題目加上「久待警報有幾次」後預期不再唯一）。2026-10-28 在雲端容器 CPU（同上表第一列的環境，題目為現行文字）量完整 35 題：34／0／1，V25「上了幾次廁所」沒對應到（改列選單），中位數 0.70 秒。Jetson 上 2026-10-29 量過完整 35 題，結果相同（34／0／1，0.42 秒，上方記錄表）。
- 「機器還活著嗎」（V29）與「系統是否正常？」（`--scope-questions` 的 F1，Demo 試用時讀者實際打的）：2026-11-04 在 Jetson 上用 `jetson-demo-ask-v2`、`event-prompt-v3` 時都沒對應到、改列選單（V29 是三份題組的量測，見上方記錄表；F1 是同日在 Demo 頁面手動問的，不在那次 372 題內）；V29 在本機對到 offline。2026-11-04 決定維持現狀，不加進 `EVENT_SCOPE.known`、不改題目文字；預期仍寫 offline，對到算正確、改列選單算沒對應到。offline 只答得到有沒有斷線，「系統正常」範圍更廣，讀者從選單點題即可。`--scope-questions` 因此是 373 題。
- 題組只收預期唯一的寫法。2026-10-28 另外試過、沒有收進題組的：「阿嬤有出來嗎」「廁所那邊還好嗎」太含糊，Gemma 4 E4B 都回 0（改列選單）；「有人跌倒或待很久嗎」這種一句問兩件事，模型只能回一個題號，只答到第一件（要支援得改回覆格式，屬單向門）。

**選單範圍（2026-11-04，[#76](https://github.com/vincenttpe/Radar_Dev/issues/76)，同日已在 Jetson 上量）**

模型會依主題對題：「跌倒的人有沒有受傷」「今晚會不會有人跌倒」都對到 falls。現有題組沒有這類問法。修法是 `event_ask.EVENT_SCOPE`，分三層：規則先擋字面明確的問法與超過 20 字的長句、提示詞加範例、對到題目後再問模型一次（`event-prompt-v3`、`jetson-demo-ask-v2`）。

本機量測（Apple M1 Pro 16GB、Ollama 0.40.14、`gemma4:e4b` nvfp4、`--reasoning-effort none`）。每一批題目都由沒看過修法的代理撰寫，在當時的修法定案後只跑一次：

| 批次（7 題選單） | 陷阱題數 | 修法前對錯題 | 修法後對錯題 | 有答案 40 題：修法後正確 | 當時的修法 |
|---|---|---|---|---|---|
| C | 40 | 34 | 3 | 39 | 規則、範例、再確認 |
| D | 60 | 沒量 | 2 | 38 | 再加代辦、趨勢、預測、醫療的規則 |
| E | 60 | 29 | **2** | 37 | 再加長句規則（**現行版本**） |

- **新問法只能壓低，不會歸零。** E 批剩下的是「這個警報真的很煩欸」「我昨天看的電影有一幕老人跌倒」，都不是在問問題。兩輪都剩 2 題，再加規則只是追新句型，每批都會出現沒看過的。
- **剩下的靠確認步驟**：對到題目後仍要讀者按「是」才顯示答案。
- **6 題選單**（`radar-ask`、Dashboard），E 批，交班的 4 題改為應回 0：應回 0 的 64 題有 3 題對錯（多「明明沒人在卻響警報，是不是壞了」）；有答案的 36 題 31 題正確、5 題沒對應到。
- **代價**：對到題目時多一次模型呼叫，本機每題延遲中位數從 0.12～0.42 秒升到約 0.5～1.2 秒；有題目的問法少部分改列選單，「警報的處理步驟」「使用次數」這類較容易。
- **審查後加入的問法（PR #79）**：V11、V25、V28 被範圍限制改列選單，審查決定要對得到。提示詞不動，寫在 `EVENT_SCOPE.known`：完全相符就對到題目、不經過模型，仍要讀者確認。之後本機 `--demo-questions` 41／0／0、`--event-questions` 35／0／0；`--scope-questions` 372 題（F1 收進題組之前）358／2／12，對錯題是上面 E 批那 2 題，上表的數字不受影響。Jetson 上 40／0／1、34／0／1、361／1／10（上方記錄表 2026-11-04），固定題組的對錯題是 0；scope 的對錯題沒有變多，換成另一題（BT38）。
- 只用規則的結果不足：第一次只用規則時，開發題全對，換一批沒看過的題目還有 21／40 對錯。
- 限制：題組的預期和 `EVENT_SCOPE` 的內容已在 PR #79 審查確認；量化與 Jetson 不同，2026-11-04 已在 Jetson 上量（上方記錄表）；每題只跑一次。用 `radar-model-eval … --scope-questions` 重量（373 題，含 F1；A～D 批已用來調整，只有 E 批還算獨立，之後改修法再量也不算了）。

## 5. 決策順序

1. 品質：能通過輸出檢查的最小模型。
2. 記憶體：這個模型加上其他服務放得下，且有 30% 餘裕。
3. 速度：在批次時段內只用一半時間跑完。
4. 其他：價格、功耗與散熱（機構現場的安裝環境）、工作溫度範圍、供貨與 JetPack 支援年限。

滿足 1～3 的最便宜型號就是答案；不足時，先檢查範本與快取能不能再多攔一些，再考慮升級硬體或加機器（B7～B9）。
