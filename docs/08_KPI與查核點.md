# KPI 與查核點（2026-10-12 定案）

專案期程 2026-10-02 至 2027-03-31。以下是已定案的規格目標，結案時依此驗收。本 repo 只負責其中一段（知識圖譜等級判定與各 Profile 的報告，見 `02_目標架構.md`「本 repo 的範圍」），所以每一項都註明本 repo 的角色，以及目前還缺什麼才量得出來。

## 必要 KPI（結案驗收）

| # | KPI | 目標 | 定義與驗證方式 | 本 repo 的角色 | 目前缺什麼 |
|---|---|---|---|---|---|
| 1 | 照護負擔下降 | ≥ 20% | 降低護理人員巡浴廁的頻率；以護理活動工時與頻率調查表驗證 | 間接：報告與照護紀錄草稿減少巡視與書寫的需要 | 導入前的基準數據（由場域調查） |
| 2 | 系統運行可靠度 | 99% | 核心功能（感測、事件判斷、告警與資料存取）每月約 720 小時，非預期中斷 ≤ 7.2 小時 | 本 repo 的服務若算進「資料存取」，也要量自己的中斷時間 | 裝置在線／離線時段（MQTT 規格已有 `online`、`offline`，但送出條件待會議清單 D3） |
| 3 | 系統緊急通報時間 | < 10 秒 | 異常事件發生到護理人員接獲通知；事件發生時間減通知時間；以儀表板事件紀錄驗證 | 不在本 repo（即時警示路徑） | **事件發生時間**：MQTT payload 沒有時間戳（會議清單 A4），只有收到時間就量不出這項 |
| 4 | 偵測準確率 | ≥ 90% | 異常行為偵測；人工標註比對 | 不直接負責；本 repo 的報告引用這些事件 | 人工標註過的場域資料（會議清單 A10） |
| 5 | 漏報率 | ≤ 10% | 異常行為偵測；人工標註比對 | 同上 | 同上 |

結案後三年的延伸目標：偵測準確率 95%、漏報率 5%、緊急通報時間逐年縮短到 < 8 秒、< 5 秒。

**與既有延遲目標的關係**：`02_目標架構.md` 與待確認事項第 3 項的「端到端 2–3 秒」是內部目標；驗收值是 KPI 3 的 < 10 秒，兩者並存。

## 場域驗證指標

| 指標 | 驗證方式 | 目標 | 與本 repo 的關係 |
|---|---|---|---|
| 活動偵測成功率 | 人工標註比對 | ≥ 90% | 上游；活動量的可信度依此 |
| 跌倒偵測準確率 | 標註事件比對 | ≥ 90% | 上游 |
| 延遲 | 觸發事件到通報送出的端到端時間 | ≤ 10 秒 | 上游（同 KPI 3） |
| 誤拒率 | 正常求助或確認對話被錯誤拒絕的比例 | < 3% | 上游（語音） |
| 異常事件漏報率 | 場域紀錄 | ≤ 10% | 上游 |
| 突發事件反應時間 | 系統與人工比較 | 縮短 ≥ 30% | 上游為主 |
| 決策建議輸出 | 系統與人工比較 | 見下方 | **本 repo** |

**決策建議輸出**定位為照護人員的輔助資訊，輸出包括事件摘要、處置提示與照護紀錄草稿。定案的例句：「偵測到接近地面姿態持續 30 秒，未取得有效語音回應，請到場確認。」這和本 repo 的原則一致：事實由規則決定，句子以範本為主，在地模型只改寫（`02_目標架構.md` 原則 2、「在地模型負載與分流」）。這句可以直接當第一個範本。

導入後的效益指標（導入前後比較）：

| 指標 | 目標 | 與本 repo 的關係 |
|---|---|---|
| 跌倒事件即時發現率 | ≥ 90% | 上游 |
| 夜間異常事件漏報率 | ≤ 10% | 上游 |
| 夜間巡房次數 | 降低 ≥ 30% | 間接 |
| **照護紀錄撰寫時間** | **降低 ≥ 50%** | **本 repo**：照護紀錄草稿的品質決定這一項 |
| 單位人力照護負擔 | 顯著下降（問卷與工時分析） | 間接 |

## LLM 文字生成指標

| 指標 | 目標 |
|---|---|
| BLEU-1 | ≥ 44 |
| BLEU-4 | ≥ 5 |
| ROUGE-1 | ≥ 31 |
| ROUGE-L | ≥ 28 |
| BERTScore | ≥ 80 |

這些都是「模型輸出」對「人寫的參考文字」的相似度，所以要先有**參考照護紀錄**（同一段事件，由護理人員寫的紀錄）才能評估。本 repo 目前沒有參考資料，也沒有評估程式（會議清單 F13）。

## 規格與本 repo 現況的落差

| # | 落差 | 影響 | 怎麼處理 |
|---|---|---|---|
| 1 | 雷達語言模型在規格中**屬於雲端**，做法是把雷達點雲轉成語意 token 再由語言模型產生動作描述（B3、B4）；本 repo 定為 **Jetson 上的在地小模型**，只讀動作狀態 JSON、不碰點雲 | 兩者的輸入、部署位置與交付物不同，可能重工或漏做 | 會議清單 F12：確認本 repo 負責 B4 的哪一段，與雲端的雷達語言模型怎麼銜接 |
| 2 | KPI 3 要用事件發生時間計算，MQTT payload 沒有時間戳 | 結案時量不出 KPI 3 | 會議清單 A4 標為驗收必需 |
| 3 | KPI 2 要算每月中斷時間，在線時段的來源未定 | 量不出可靠度 | 會議清單 D3 標為驗收必需 |
| 4 | LLM 指標需要參考照護紀錄，本 repo 沒有參考資料也沒有評估程式 | B4 與 LLM 指標無法驗收 | 會議清單 F13；有參考資料後，本 repo 加評估指令 |
| 5 | KPI 4、5 以人工標註比對驗收，目前沒有標註資料 | 本 repo 的報告引用的事件準不準，無從得知 | 會議清單 A10 補上驗收用途；E1 之後的場域資料是第一個來源 |
| 6 | 規格的語音關鍵詞是國語、台語、英語；本 repo 文件只寫國語、台語 | 語音確認與長者本人的報告語言 | 文件補上英語；長者本人的輸出語言仍依 F6、F8 |
| 7 | 規格的驗證場域是單人使用的高隱私空間，尚未支援多人重疊 | 與本 repo「沒有 ID 不推測是誰」一致 | 不需調整；多人場域仍依 D4 |
| 8 | 照護紀錄撰寫時間要降低 ≥ 50% | 照護紀錄草稿是本 repo 最直接影響 KPI 的輸出 | Profile 的優先順序：居服員（照護紀錄草稿）先做 |
