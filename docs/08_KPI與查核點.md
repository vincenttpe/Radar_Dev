# KPI 與查核點（2026-10-12 定案）

專案期程 2026-10-02 至 2027-03-31。以下是已定案的規格目標，結案時依此驗收。本 repo 只負責其中一段（知識圖譜等級判定與各 Profile 的報告，見 `02_目標架構.md`「本 repo 的範圍」），所以每一項都註明本 repo 的角色，以及目前還缺什麼才量得出來。

## 必要 KPI（結案驗收）

| # | KPI | 目標 | 定義與驗證方式 | 本 repo 的角色 | 目前缺什麼 |
|---|---|---|---|---|---|
| 1 | 照護負擔下降 | ≥ 20% | 降低護理人員巡浴廁的頻率；以護理活動工時與頻率調查表驗證 | 間接：報告與照護紀錄草稿減少巡視與書寫的需要 | 導入前的基準數據（由場域調查） |
| 2 | 系統運行可靠度 | 99% | 核心功能（感測、事件判斷、告警與資料存取）每月約 720 小時，非預期中斷 ≤ 7.2 小時 | 本 repo 的服務若算進「資料存取」，也要量自己的中斷時間 | 裝置在線／離線時段（MQTT 規格已有 `online`、`offline`，但送出條件待會議清單 D3） |
| 3 | 系統緊急通報時間 | < 10 秒 | 異常事件發生到護理人員接獲通知；**通知時間減事件發生時間**（2026-10-18 更正，原文寫反）；以儀表板事件紀錄驗證。終點是哪一次通知待決定，見下方「KPI 3 的量測起點與終點」 | 不在本 repo（即時警示路徑） | **事件發生時間**：MQTT payload 沒有時間戳（會議清單 A4），只有收到時間就量不出這項 |
| 4 | 偵測準確率 | ≥ 90% | 異常行為偵測；人工標註比對 | 不直接負責；本 repo 的報告引用這些事件 | 人工標註過的場域資料（會議清單 A10） |

結案後三年的延伸目標：偵測準確率 95%、漏報率 5%、緊急通報時間逐年縮短到 < 8 秒、< 5 秒。

### KPI 3 的量測起點與終點（待決定，2026-10-18）

同一份規格裡有兩種寫法：KPI 3 是「發生到護理人員**接獲**通知、< 10 秒」，場域驗證指標「延遲」是「觸發事件到通報**送出**、≤ 10 秒」。裝置偵測到跌倒後還會先語音詢問、等 10 秒再重問一次（待確認事項第 4 項），所以選哪一次通知當終點，決定這項達不達得到。

| 選項 | 起點 | 終點 | 影響 |
|---|---|---|---|
| a（建議） | 裝置判定跌倒的時間 | 預警送達護理人員的裝置（推播到達） | 前提是預警和語音詢問同時進行、不等回覆（待確認事項第 3 項）；起點要由裝置帶上發生時間（A4） |
| b | 同上 | 語音詢問逾時後的通知 | 光等待就超過 10 秒，「< 10 秒」不可能達成 |
| c | 同上 | 護理人員按「已收到」 | 含人的反應時間，不只是系統表現 |

選定之後，KPI 3 與場域驗證指標「延遲」要改成同一種寫法（「< 10」或「≤ 10」也要一致）。週一資訊需求 2-8（`14_週一資訊需求_2026-10-19.md`）。

**與既有延遲目標的關係**：`02_目標架構.md` 與待確認事項第 3 項的「端到端 2–3 秒」是內部目標；驗收值是 KPI 3 的 < 10 秒，兩者並存。

## LLM 文字生成指標

| 指標 | 目標 |
|---|---|
| BLEU-1 | ≥ 44 |
| BLEU-4 | ≥ 5 |
| ROUGE-1 | ≥ 31 |
| ROUGE-L | ≥ 28 |
| BERTScore | ≥ 80 |

這些都是「模型輸出」對「人寫的參考文字」的相似度，所以要先有**參考照護紀錄**（同一段事件，由護理人員寫的紀錄）才能評估。本 repo 目前沒有參考資料（會議清單 F13）。

**2026-10-17**：評估程式已有。照護紀錄由在地模型改寫（`src/radar_agent/care_record.py`，沒通過檢查就退回一行一事件的草稿），`radar-model-eval --records --references 參考紀錄.json` 以字為單位計算 BLEU-1、BLEU-4、ROUGE-1、ROUGE-L 並對照上表目標（`text_metrics.py`）；`--style` 可放機構格式樣本。BERTScore 需要另外的語言模型，尚未計算。拿到機構的參考紀錄與格式樣本後，就能量第一次的數字。

### B4 交付規格草案（待會議清單 F12 決定，2026-10-18）

「居服員 Profile 先做」決定的是開發順序，B4 由誰交付還沒定。下面是本 repo 這一側的草案，供會議決定時對照：

| 項目 | 草案 |
|---|---|
| 負責人 | 待定：本 repo（Jetson 上的在地模型），或雲端的雷達語言模型；也可能兩邊分段（雲端產生描述句、本 repo 產生紀錄） |
| 輸入 | 裝置事件（`docs/adr/0001`）整理出的事件；radarLLM 的描述句只當補充，不決定內容 |
| 輸出 | 照護紀錄：先是一行一事件的草稿（`event_notes()`，例：「09:06 1 號廁所雷達偵測到疑似跌倒，語音詢問 10 秒未獲回應。」），再由在地模型改寫成機構格式（`care_record()`，沒通過檢查就退回草稿） |
| 驗收 | (1) 事實一致：人工核對每份紀錄，時間、事件、次數沒有錯、沒有漏、沒有多（目標 100%）；(2) LLM 文字指標對照參考紀錄（下一節）；(3) 撰寫時間降低 ≥ 50%（`15_照護紀錄撰寫時間量測.md`） |

### LLM 文字指標的評估規格（2026-10-18）

| 項目 | 規格 |
|---|---|
| 參考紀錄 | 護理人員就同一段事件寫的照護紀錄（F13），去識別後存成 `{題號: 紀錄}`；每段事件至少一份，題組要涵蓋跌倒、回覆沒事、主動呼救、久待、斷線 |
| 比對的文字 | 實際交給居服員的紀錄（模型輸出；沒通過檢查時是草稿） |
| 斷詞 | 以「字」為單位，空白不算 |
| 計分尺度 | 0～100 |
| BLEU-1、BLEU-4 | 整份題組一起算：clipped n-gram precision 的幾何平均乘上長度懲罰，不做平滑 |
| ROUGE-1、ROUGE-L | 每對算 F1，再取平均 |
| BERTScore | 待定：中文預訓練模型的名稱與版本、取哪一層，選定後寫在這裡，每次評估記下版本 |
| 指令 | `radar-model-eval --records --references 參考紀錄.json [--style 機構格式樣本.txt]`（`text_metrics.py`） |
| 事實一致 | 文字相似度不能證明紀錄正確。採用前程式會檢查（數字要來自事實、不能漏掉時間、不能多加句子、斷線要寫「狀況不明」）；驗收時另做人工核對，見上一節 |

斷詞方式與計分尺度要和甲方或合作學校確認，是否與計畫書驗收時的算法一致。
