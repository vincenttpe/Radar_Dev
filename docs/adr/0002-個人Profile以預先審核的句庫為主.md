# 個人 Profile 以預先審核的句庫為主，在地模型只補句庫做不到的部分

知識圖譜等級給醫師、家屬、長者本人看的文字，主要路徑是**句庫**：依「指標 × 等級 × Profile × 知識圖譜版本」事先寫好、經審核人核准的句子。Jetson 執行時只查表、填數字，不呼叫模型。在地模型只用在句庫做不到的地方，例如把多個指標寫成一段綜合摘要，而且輸出仍要經過 `rewrite()` 的檢查，沒過就退回句庫。

理由：

- 輸出的種類有限：知識圖譜 v1 共 5 個指標、24 個等級（`kg/v1/thresholds.json`）。每種讀者 24 句，醫師、家屬、長者本人三種約 72 句；加上「比上次變好／持平／變差」也只有幾百句，人可以逐句審完。
- 品質：句子事先由人看過，不會出現模型臨時加上的內容。決策單 D-4 的實例（2026-10-17，PR #45）顯示，模型多加一句「每 3 小時巡視一次」，只因範本裡剛好有「3 分」就通過了檢查；句庫沒有這個風險。
- 算力：Jetson 的 CPU 與 GPU 共用記憶體（`docs/06`），查表幾乎不耗資源，個人報告不再決定 Jetson 型號。
- 追溯：每段文字記下句庫版本與核准紀錄（原則 3），同樣的事實每次產生同樣的文字。

## 考慮過的做法

- **在地模型即時改寫，範本當備援**（原本 `docs/02` 的分層）：說法較多變化，但每次輸出都要靠檢查把關，檢查擋不到的錯（D-4 的對調與多加句子）會直接送到讀者；模型負載也隨長者人數成長。
- **只用範本，不分讀者**：最簡單，但同一句話很難同時適合醫師與家屬（`docs/02`「輸出的對象」）。

## 後果

- `docs/02`「在地模型負載與分流」的分層加上句庫一層，放在範本與快取之間；在地模型改成只處理句庫沒有的組合。
- 句庫內容屬單向門「給讀者的輸出與用語」：新增或改句子要經審查與審核人核准，和知識圖譜升版一起處理；知識圖譜升版時，句庫要重新產生、重新核准。
- 先做**家屬**一種讀者，驗證「產生 → 審核 → 查表」的流程，再擴到醫師與長者本人。個人報告要到老人公寓（一台雷達只看一個人）才用得到；Demo 的廁所沒有個人 ID。
- 句庫可以在算力夠的機器上事先產生草稿，但草稿只能用知識圖譜的事實與原文；送進產生工具的不能有姓名或長者代號。
- 知識圖譜尚未核准時（K-2），句庫一樣要標「僅供測試」。
- 居服員的場域摘要（`caregiver.py`）本來就是固定範本，不受影響。
