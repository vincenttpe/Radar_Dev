# 以裝置事件為主要輸入，描述句只當補充

雷達有兩份各自獨立產生的資料：裝置自己判斷出的**裝置事件**（`mode`／`event`／`trigger`／`userReply`），以及 Jetson 上 radarLLM 從點雲寫出的**描述句**（`Timestamp`／`Motion`／`Speed`／`fall`）。本 repo 的次數、時長、在線時段與跌倒判定一律以裝置事件為準；描述句只用來補充說明「當時的動作」，不拿來計數或判定等級。

理由：

- C2 已定跌倒次數以裝置事件的 fall 為準（2026-10-13 書面回覆，已確定）。
- 裝置事件是固定欄位、固定列舉值（A3），可以檢查；描述句是語言模型產生的文字，可能看錯或寫錯，同樣的點雲也不一定寫出同樣的句子（A21）。
- 10/09–10/13 的資料顯示，裝置事件約每 5 秒一筆（沒人時也送），可以切出造訪、算停留時間與在線時段（A6、A10、D3）；描述句做不到。

## 考慮過的做法

- **以描述句為準**（原本的設計）：描述句本來就送到 Jetson，不必另接資料；但跌倒次數會和 C2 的定義不同，數字也建立在模型輸出上。
- **兩者並用、互相比對**：描述句的 `fall` 從哪來還不知道（A22），兩邊不一致時沒有判準，先不做。

## 後果

- 前提是 Jetson 收得到裝置事件。A23 回覆 Jetson 與雲端目前是各自獨立的系統、計畫整合；A32（2026-10-14）確認 Jetson 訂閱的 topic 已包含所有裝置事件，只要裝置與 Jetson 在同一個網路即可收到。若部署時不在同一個網路而收不到，這個決定要重新檢討，不能默默改用描述句計數。
- A22 回覆跌倒以裝置邊緣端的判斷為主，與本決定一致。
- A30 確認「回答沒事」是 `resolved` 加 `noNeedHelp`；描述句沒有這個資訊，也是以裝置事件為準的理由之一。
- 裝置事件目前沒有序號（A11，短期可加），接收端要自己去除重複紀錄；加上序號後改用序號。
- 裝置斷線期間（在線時段之外），報告寫「無法判斷」，不寫「0 次跌倒」。`fallSwitch` 不是偵測開關（A31），不能拿來判斷偵測有沒有開。
