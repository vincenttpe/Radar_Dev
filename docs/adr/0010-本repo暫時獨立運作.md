# 本 repo（Jetson 端）暫時獨立運作，Dashboard 負責人以協作者身分參與

本 repo 產生的是 Jetson 端的報告文字、提問答案與使用趨勢（ADR 0007），不影響原本的雷達設備，也不影響 Dashboard 的 repo 運作。在兩邊正式整合之前，本 repo 暫時獨立開發、獨立發版：不改雷達設備的韌體或設定，不改 Dashboard 的程式，也不連真實雲端（ADR 0009：Dashboard 負責人確認 API 前，只用本機的假 Dashboard 與模擬資料測試）。

為了將來整合，Dashboard 負責人加入本 repo 當協作者，直接在這裡看文件、開 issue、送 PR、審查和 Dashboard 有關的改動。

## 兩邊的接點

整合時只靠下面兩份約定，兩邊各自的內部做法都不必遷就對方：

- `docs/23_Dashboard連線API草案.md`：Jetson 向 Dashboard 取需求、取裝置事件、傳回結果的 API（ADR 0009）。
- `docs/16_Dashboard對接說明.md`：傳回的 JSON（`caregiver-report-v0`、`usage-trend-v0`、`event-ask-v0`）的欄位與顯示規則。

這兩份由本 repo 維護，Dashboard 負責人可以直接改或提出修改；改了之後，兩邊的程式都要跟著改，所以要在 PR 裡寫明影響。交接的整理見 `docs/24_Dashboard負責人交接_2026-11-03.md`。

## 考慮過的做法

- **直接併進 Dashboard 的 repo**：Jetson 端要跑在地模型、讀知識圖譜，部署方式和 Dashboard 不同（`docs/20`）；長期架構也還沒定（沒有 Jetson 的機構怎麼辦、知識圖譜怎麼導入，見 `docs/24`「長期架構」）。現在合併，等於提早綁定架構。
- **各自開發、只用文件交接**：約定改了另一邊不容易知道，交接文件也容易過時。讓 Dashboard 負責人當協作者，約定的修改就能在同一個 PR 裡討論與審查。

## 後果

- 協作者的改動照本 repo 的規則審查：PR 範本、`REVIEW.md` 的單向門、合併前的 code-review（`CLAUDE.md`）。碰到單向門的改動，由 repo 擁有者核准後才合併。
- GitHub 的協作者權限由 repo 擁有者在 GitHub 設定。個人帳號的 repo，協作者一律是寫入權限，所以建議在 `main` 設定「必須經過 PR、至少 1 人核准」，並開啟 Actions，讓 pr-gate 與測試在協作者的 PR 上自動跑。這兩項是 repo 設定，不在 repo 的檔案裡。
- Issue 都記在本 repo（`vincenttpe/Radar_Dev`）。原本的 `Deepfens-AI/Radar_Agent` 已封存，只剩舊紀錄（`docs/agents/issue-tracker.md`）。
- 長期架構定了之後（例如沒有 Jetson 的機構改用雲端範本層），要另寫 ADR 取代或補充本篇。
